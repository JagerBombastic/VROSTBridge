# VROSTBridge 1.0.0.14

What the first external testers and 1.0.0.13's first session asked for: a sharper picture and hands that land where they were swung. Every package carries **1.0.0.14**, and the [1.0.0.13 notes](history/RELEASE_1.0.0.13.md) still apply.

**Install** over 1.0.0.13 on each PC: `VROSTBridge-Host-Setup-1.0.0.14.exe` on the rendering PC, and `VROSTBridge-Bazzite-Installer-1.0.0.14.zip` or `VROSTBridge-Client-Setup-1.0.0.14.exe` on the headset PC. Settings, pairing, the network test, Baballonia and its calibration stay. Nothing on the wire changed, so either PC still works with the other at 1.0.0.13; each change below belongs to one PC and comes with that PC's package.

## What changed

The testers found the latency good and the foveation invisible, and asked for two things: notes in a rhythm game that they had clearly swung at were missed, and fine detail (snow, foliage, chain-link fences) was softer than on a directly connected headset. Testing this build turned up two more things, both answered here: a headset PC on its network twice (cable and Wi-Fi) received the video over Wi-Fi, and Windows calling the home network Public stopped every session.

- **One network, two adapters** (Bazzite). A headset PC on the home network by cable and by Wi-Fi at once has two addresses on one network, and Linux answers for either address on either adapter. In the first 1.0.0.14 session with Wi-Fi left connected, the host sent the video to the cable's address and the Wi-Fi card took it: 7.5 million packets over Wi-Fi, 77 thousand over the cable, and every five minutes or so Wi-Fi's background scan stalled the picture for a few seconds. VROSTBridge used to disconnect the other Wi-Fi adapter for each session instead, which depends on the system leaving the cable's route alone; on one PC it did not, and every Start failed with the host unreachable. Now the page offers **Fix this PC's network settings** when this PC is on its network more than once: two standard Linux settings (each adapter answers only for its own address), one password prompt, kept across restarts. After that Wi-Fi stays connected during sessions and the video stays on the cable. Without it VROSTBridge still pauses the other Wi-Fi adapter, but checks the host is reachable over the cable straight afterwards and reconnects Wi-Fi at once if not. A session whose video arrives on another adapter than the one chosen now says so, on the page and in the log (`VIDEO_PATH`). Windows needs none of this.
- **The receive buffer, judged properly** (Bazzite). The same page item covers a receive buffer too small for the stream. 1.0.0.13's lost frames had been put down to it, wrongly: the stream's socket gets twice the system limit, which on Bazzite is already 8 MiB, close to a second of video. Only a limit that leaves the stream less than 4 MiB (a stock Linux kernel's) is reported. The reports carry the stream and gaze sockets' own drop counters, so the next one says which socket, if any, overflows.
- **Any network type on Windows.** The rendering PC refused every session until Windows classed the network as Private, and Windows reclasses a network as Public whenever it decides it is new. Headset PCs already paired now start sessions on any network type. The firewall rules still admit only the local subnet (they are updated once, with one administrator prompt, after installing), and a *new* headset PC still pairs itself automatically only from a network Windows classes as Private, so a stranger on a café network cannot. The Windows client's firewall rules follow suit.
- **HEVC for every headset.** *Auto* codec chose H.264 for everything but a Beyond, so Index testers ran the weakest codec at the lowest ceiling. It now chooses HEVC, 10-bit where the headset PC decodes it, and H.264 only on a PC whose decoder has no HEVC. For that, the Bazzite client asks VA-API which profiles the GPU decodes (the Windows client already asks Direct3D 11) and the companion remembers the answer, so the choice is right before the first Start.
- **Rendered larger than it is streamed** (rendering PC). A headset on its own PC renders at SteamVR's recommended size, larger than the panels, to make up for the lens distortion. Until 1.0.0.13 the host rendered at the stream size, so the far field was already softened before the encoder saw it. The host now renders at the size the headset PC's SteamVR recommends, at most one and a half times the stream, and scales it down for the encoder: more detail in each streamed pixel, for GPU time on the rendering PC, which has it to spare. SteamVR's resolution setting on the rendering PC changes that render size, not the stream.
- **More bits per pixel.** The automatic bitrate was capped at 0.22 bit per encoded pixel for HEVC, a ceiling the testers' links and decoders were well under while fine texture still smeared. It is 0.30 now (0.42 for H.264, 0.25 for AV1): about a third more for the same stream, when the network test and the decoder allow it. The link's measured rate and the governor's steps still apply.
- **Hands predicted with their acceleration** (headset PC). The rendering PC predicts every pose a measured latency ahead, 30 to 40 ms on a wired link, from its velocity alone. A hand that is speeding up or slowing down, which is most of a swing, lands short or long by half its acceleration times the latency squared: about 18 mm for a brisk swing, more at the end of a fast one. The client's own check measured the host landing up to 170 to 280 mm from where a controller really was in the 1.0.0.13 session. The client now estimates each controller's acceleration from consecutive tracking samples, smoothed and bounded, and folds it into the pose and velocity it sends, so the host's own extrapolation lands where the hand will be. The poses on the wire are the same poses, so a 1.0.0.13 host gains it too. The check in the report now measures the host's result against the real pose.
- **The sharp region predicted through the head's turn** (eye tracking). The gaze reaches the rendering PC the stream's latency old, and during a head turn the eyes counter-rotate to hold a point, so the region landed behind where you were looking. The client turns the gaze sample by the head's angular velocity over that time (bounded at about 20°) before sending it.
- **The host keeps its last session's statistics.** The 1.0.0.13 host report arrived empty because the host's VROSTBridge had been restarted between the session and the report. The host now writes what it measured every minute and at Stop (`host-last-session.json` in its state folder), and a report made with no session since the companion started carries it as `host_last_session`.
- **The menu button** is confirmed: a short press opens the rendering PC's SteamVR menu (a tester quit the game from it).

## How to test

Play as before, wired, with *Use recommended settings* and *Pause other Wi-Fi adapters on this network* on, and send both reports. On Bazzite with Wi-Fi connected too, the page offers *Fix this PC's network settings*: use it once (one password prompt). Then Start: Wi-Fi stays connected, the page shows no *video is arriving over* note, and the report's `adapter_counters` show the stream adapter receiving the video, not Wi-Fi. The choppy few seconds every five minutes should be gone. On the rendering PC, accept the one administrator prompt after installing (the firewall rules are updated), and a Public network no longer stops anything. The log's *Stream:* line names HEVC on an Index, the render size beside the stream size, and a higher bitrate ceiling than 1.0.0.13's; the picture's far field should be sharper at the same stream size. In a rhythm game, notes swung at should register, and the report's controller prediction check (its 95th percentile) should be well below the 1.0.0.13 session's. With eye tracking, the sharp region should stay where you look during head turns. Save the host report after the session even so: `host_last_session` is a record of the session's statistics, not the whole report.

## Known limits

- A rhythm game is the worst case for a streamed headset: the hands are tracked on one PC and the game runs on another, a stream's latency apart. Acceleration takes the predictable part of a swing out of that; a change of direction within the latency cannot be predicted by either PC.
- The render size follows what the headset PC's SteamVR recommends, so a headset PC set to a low SteamVR resolution gives the rendering PC less to render; *Auto* and the stream size are unchanged by it.
- VROSTBridge doesn't switch a Beyond between its 75 and 90 Hz modes: set the mode with Bigscreen's Beyond Utility on a Windows PC. 144 Hz on an Index is experimental: if SteamVR won't start at it, choose 120 Hz.
- The rendering PC's occasional stalls are not fixed; they still cost no bitrate.
- Starting a session from Game Mode on Bazzite is unconfirmed (use Desktop Mode), and the Windows client hasn't run on real hardware.
