# Implementation status — 2026-10-18 / 1.0.0.14

Baseline: **VROSTBridge 1.0.0.14**, one version for every package: the Windows host, the Bazzite client and the Windows client. 1.0.0.11, 1.0.0.12 and 1.0.0.13 are published on GitHub; 1.0.0.14 is built and tested, and its release text is ready in [GITHUB_RELEASE_1.0.0.14.md](GITHUB_RELEASE_1.0.0.14.md).

Complete contracts are in [PROJECT_SPEC.md](PROJECT_SPEC.md), how it works and its known limits in the [technical reference](TECHNICAL_REFERENCE.md), and the test evidence in [BUILD_VERIFICATION.md](BUILD_VERIFICATION.md). ## From the first testers and the first session of 1.0.0.13 (1.0.0.14)

The testers found the latency good and the foveation invisible, missed notes they had swung at in a rhythm game, and found fine detail softer than on a directly connected headset; testing the first build found a headset PC on its network twice receiving the video over Wi-Fi, and a Public network on the rendering PC stopping every session. 1.0.0.14 answers each: the hands' acceleration folded into the poses (`client/device/acceleration.hpp`), the host rendering at the recommended size (`host/profile.py`), HEVC as *Auto* with VA-API's profiles read on Bazzite, a ceiling about a third higher (`launcher/stream_budget.py`), *Fix this PC's network settings* with the Wi-Fi pause made safe and the video path checked (`launcher/network_settings.py`, `launcher/wifi_others.py`), any Windows network type for paired headset PCs (`host/control.py` and the firewall scripts), the gaze predicted through the head's turn (`client/device/gaze_prediction.hpp`), and the host's last session kept (`launcher/last_session.py`). Its first session kept the video on the cable, held the GPU clock from the start and cut the worst prediction miss by about 40 %. Checks: `tests/test_vrostbridge_1014.py`, `tests/acceleration_tests.cpp`, `tests/gaze_prediction_tests.cpp`.

## From the first session of 1.0.0.12 (1.0.0.13)

The decoder fell behind at the highest bitrate and the wired link lost packets in clumps. 1.0.0.13 doubled the parity on a wired link, stopped promptly while the rendering PC's SteamVR starts, offered the stream choices before a session, and added the adapters' drop counters, the remembered GPU clock and where Game Mode's SteamVR came from to the reports. Its hour-long session confirmed the parity and the stream choices (`tests/test_vrostbridge_1013.py`).

## From the first session of 1.0.0.11 (1.0.0.12)

The bitrate stayed low after a slow start, the GPU clock was found late, and the add-on warning listed SteamVR's own drivers. 1.0.0.12 restarts the bitrate when the GPU clock is raised, doesn't count seconds the rendering PC sent nothing, remembers the clock for the next session, and warns only about add-ons from outside SteamVR. Its first session confirmed the bitrate and the add-on warning; the clock was first held from the start in 1.0.0.14's (`tests/test_vrostbridge_1012.py`).

## A lighter picture on the headset PC (1.0.0.11)

So that a headset's full resolution fits lighter headset PCs: the frame pass's foveation terms worked out once per frame (about a third less work per pixel), the pixels the lenses never show skipped, each eye shown at 90 % then 80 % while the graphics fall behind, and the pass and plane copy timed on the GPU. On hardware the pass took 1.9 ms a frame at the Beyond's full size, and the lens area kept 99.7 % of the Beyond's pixels; the step smaller hasn't yet been needed on hardware (`tests/test_vrostbridge_1011.py` and the C++ shader and frame-path tests).

## Windows client

A Windows 10 or 11 PC can be the headset PC: the same native client, page and stream, decoding through Direct3D 11 (D3D11VA) with a copy into the frame pass, Baballonia's Windows installer for a Beyond 2e, a tray icon, start at sign-in, firewall rules for the local subnet in one step, Wi-Fi media streaming mode during sessions, *Best performance* while streaming, and a per-user installer or portable ZIP. Its parts are tested in code and under Wine, but it hasn't run on a Windows PC with a headset: Wine has no Direct3D 11 video decoder, so D3D11VA, the copy's cost, Windows Firewall, the Wi-Fi and power calls, and Baballonia's Windows install have run nowhere. The [hardware acceptance list](HARDWARE_ACCEPTANCE.md) has a check for each part, and the part-by-part table is in the [earlier status](history/IMPLEMENTATION_STATUS_EARLIER.md#windows-client-1007).

**Bazzite only:** Steam's Game Mode and its screen, *Add to Steam*, the headset display reservation and its lease helper, the eye-camera helper and *Allow eye camera access*, Baballonia's calibration launcher with its Vulkan layer, *Fix SteamVR reprojection*, *Set the GPU clock to automatic* and *Fix this PC's network settings*. On Windows they are hidden from the page, and their actions explain why if called. Done another way on Windows: the audio devices (SteamVR switches them), the access-point lock (background scanning off), and the firewall (Windows Firewall instead of firewalld).

## Immediate remaining work

1. Physically test 1.0.0.14 further (its release notes' *How to test*): the far field at the same stream, the sharp region during head turns, a Public network on the rendering PC, and `host_last_session` after a host restart; then what 1.0.0.13 left open (an Index at 120 and 144 Hz, a stop while SteamVR starts).

3. Make Game Mode start sessions: the report's `steamvr_origin` says what started SteamVR's server and which display it reached.
4. Run the Windows client on Windows hardware, starting with what no test here could reach: D3D11VA decoding, the copy's cost, the firewall, Wi-Fi and power calls, and Baballonia. A zero-copy path only if the copy shows in the timings.
5. Code-sign the Windows installers and programs before a wider release; until then SmartScreen asks (*More info → Run anyway*).
6. The older checks still open, listed in [HARDWARE_ACCEPTANCE.md](HARDWARE_ACCEPTANCE.md).

Passing tests in code don't replace these physical checks. The historical 0.1.0 Windows diagnostic (the root `VROSTBridge.exe`) is no longer built.
