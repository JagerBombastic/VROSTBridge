# Physical acceptance — VROSTBridge 1.0.0.14

This page says what has been confirmed on real hardware, what is still open, and what to record. Automated tests prove the code does what it was written to do; only a headset on a head proves it feels right, so each item here counts once its result repeats.

## Tested so far

This is the hardware VROSTBridge has been used with, by its maintainer:

| Part | Used with | Confirmed on it |
| --- | --- | --- |
| Rendering PC | Windows, an AMD Radeon desktop GPU (AMF encoder) | Streaming to both headsets |
| Headset PC | A Ryzen handheld with integrated Radeon graphics, with Bazzite, on Wi-Fi 7 and on a 1 Gbit/s USB Ethernet adapter | Desktop Mode sessions, wired and on Wi-Fi; Game Mode in part (its full check below is still open) |
| Valve Index | With Index controllers and SteamVR base stations | Picture, tracking and controllers, locally and through the bridge |
| Bigscreen Beyond 2e | With Index controllers and base stations | Picture and tracking through the bridge, at its native 2560 per eye; true blacks on its OLED panels; Baballonia's calibration in the headset over the stream; the eye-tracked foveated stream, with the eye cameras at 90 pictures a second; steady motion with the bitrate held to what the picture needs; clean game audio; sessions of twenty minutes and more without a lost frame; the controller's system button opening the rendering PC's menu |

Not tried: a headset PC running Windows (no item of [its list](#windows-headset-pc) has been checked yet), NVIDIA or Intel encoders on the rendering PC, Linux distributions other than Bazzite, other headsets (including the other Beyond models), and everything this page lists as open.

What the latest sessions showed, wired on Bazzite with a Beyond 2e: with *Fix this PC's network settings* applied, the video stayed on the cable with Wi-Fi left connected, and the five-minute stalls seen with both adapters connected went away; the host's prediction of a swinging controller landed within 100 to 160 mm at worst, against 170 to 280 mm before acceleration was sent. Two things remain: the automatic bitrate can start higher than the headset PC's decoder sustains and settle lower within the first minutes, and a demanding game can hold the rendering PC below the refresh rate (its own capture stalls, not the stream).

## Open checks

Use **1.0.0.14** on both PCs ([release notes](RELEASE_1.0.0.14.md)); over Wi-Fi, turn off Wi-Fi power saving on the client page and run the network test again first.

Picture and motion:

- **Hands where they were swung:** in a rhythm game, notes swung at register; the report's controller prediction check (`prediction` in the `INPUT` lines, its 95th percentile) stays low.
- **A sharper picture at the same stream:** the *Stream:* line names HEVC on an Index and a render size above the stream size; fine detail in the far field (foliage, fences) is sharper at the same stream size.
- **The picture's edges:** nothing at the edges of the view looks cut off or dark, also while turning the head quickly; the client log's `VISIBLE_AREA` line gives each eye's share of computed pixels, and its `STATUS Lens area` line how the headset's mesh was used. If the edges look wrong, compare with *Skip what the lenses never show* off.
- **Keeping the frame rate:** where the headset PC cannot hold the refresh at the full size, the page shows *Shown at 90 %* (or 80 %) beside the frame rate instead of the stream dropping to half rate, the log has a `SCALE` line with the reason, and the full size comes back once there is room; with *Keep the frame rate when this PC falls behind* off, the size stays at 100 %.
- **Display modes:** before Start the stream list shows the headset's choices. On an Index, 120 Hz and then 144 Hz run at that rate, and SteamVR's own refresh setting is back after Stop; on a Beyond there is nothing to choose, and the stream is 2560 in its 75 Hz mode and 1920 in its 90 Hz mode, as set with the Beyond Utility.
- **The rendering PC's stalls:** in a game, play five minutes with eye tracking on and five with it off, with reports from both PCs: the host report's `VROST_HOST_ACQUIRE` lines and SteamVR's `WaitForAcquire` warnings say whether the stalls follow the game or the gaze.

Network and bitrate:

- **One network, two adapters (Bazzite):** with Wi-Fi connected too, *Fix this PC's network settings* once; Wi-Fi then stays connected during sessions, the page shows no *video is arriving over* note, and `adapter_counters` show the video on the stream adapter.
- **A Public network on the rendering PC:** after the one administrator prompt that updates the firewall rules, a paired headset PC starts sessions with the network set to Public.
- **Lost packets:** frames lost stay rare while *Rebuilt on the way* counts, wired and on Wi-Fi, with eye-tracked foveation at the full size; both reports carry `adapter_counters`, which say whether a PC's own adapter dropped what was lost.
- **The bitrate:** with *Use recommended settings*, it holds through a session; a step down for uneven arrival comes back up, a step down early in a session goes back once the headset PC's GPU clock is held higher (*Last change: back to the start: the GPU clock was raised*), and short stalls from the rendering PC do not step it down.

The headset PC:

- **Performance balance (Bazzite):** with the charger in, the *This PC* card says what was set; the GPU clock rises when frames run late; the next session says *GPU held at … MHz from the start, as the last session needed*; Stop (or the next start after a forced quit) puts Steam's Performance settings back.
- **Base stations:** all wake at Start and sleep within about 10 s of VROSTBridge closing, on Bazzite and on Windows; on Bazzite one that does not wake is named with its signal strength.
- **Game Mode (Bazzite):** with the headset connected before entering Game Mode, Start from the Steam library entry streams, the headset PC's built-in screen staying on. If it does not, the message says why, and a report from either mode carries `game_mode_last_start`.

Eye tracking (Beyond 2e):

- **The sharp region:** it sits where you look, straight ahead included, even with an off-centre calibration, and stays on what you look at while turning the head; *Gaze reach* has no direction under 30° after calibrating with wide head turns; *Use previous calibration* and *Reset centring* do what they say.

Housekeeping:

- **Stop while the rendering PC's SteamVR starts:** it ends within about ten seconds.
- **The host's last session:** a host report made after the host's VROSTBridge restarted carries `host_last_session`.
- **The add-on warning:** the rendering PC's page names only add-ons installed from outside SteamVR (a headset maker's helper, for instance), or nothing.

Save reports before restarting a failed session when possible: use **Send report to host** on the client and download it with the host's own report on the host page.

## Record each run

Record HMD model, local display mode/effective refresh, client/host GPU and drivers, the client's power limit (TDP) setting, its GPU clock setting (automatic, or fixed and at what) and whether the charger was connected, SteamVR versions, wired/Wi-Fi route (and whether Wi-Fi stayed on one access point), frame re-aim on/off and the alignment check answer, codec and bit depth, foveation preset (and whether gaze drives it), requested/negotiated/encoded resolution, bitrate (manual or measured), pacing rate, test scene and duration. Keep one variable at a time when comparing performance. Frame age is not measured motion-to-photon latency.

## Required sequence

1. Confirm correct local SteamVR view, tracking, both controllers and room setup on the client with the bridge stopped.
2. On a Beyond, confirm stereo alignment, scale, optical centre and head-motion stability. If wrong, capture `view_geometry` and describe the distortion. Regress the Index using the same updated client.
3. Perform two cold starts and two warm Start/Stop cycles. Start only from the client. Check both runtimes close on Stop and the host returns to waiting. Check quiet host sign-in startup separately.
4. Run at least 30 minutes of a demanding game. Independently test left/right actions, trigger/grip, sticks, touches, finger poses, haptics and host dashboard. Sleep/reconnect each controller and confirm input recovery, not just pose recovery.
5. Adjust IPD during a stream and check geometry remains stable. Confirm the host rectangular play area and standing origin agree with the local setup; the local boundary remains authoritative.
6. Compare Wi-Fi and Ethernet at identical quality settings and with the intended adapter selected. Record unique frame cadence, repeated frames, frame age, host timing and client decode/conversion timing. Investigate observed half-rate episodes.
7. Exercise brief network interruption, loss of host/native process, cancellation during startup and retry. Check held/neutral remote presentation, actionable status and settings restoration. Do not deliberately disable physical boundary protections.
8. After desktop success, add VROSTBridge to Steam from the client page and validate Game Mode: the handheld's own screen stays on with the headset connected, the library artwork, the lease/display, native controls, host menu, Stop/Exit and return to desktop. Connect/power HMD before entering Game Mode.
9. If using Beyond 2e gaze, validate clear cameras, calibration after refitting, host direction, provider/camera restart and stale-data handling. With *Eye-tracked* foveation, look around without moving your head: the image must look equally sharp wherever you look, without lag, shimmer or a visible region edge. This does not qualify OpenXR gaze or foveated rendering in games.
10. Foveated encoding without gaze: compare *Off*, *Subtle* and *Balanced* in the same scene on each headset; look for edge blur, seams or eye mismatch.
11. Network and power: run the network test on Ethernet and Wi-Fi; compare pacing on/off on a slower client link; with gradual recovery on Wi-Fi check losses heal without freezes. Wake the sleeping host from the client, check it stays awake in a long session and sleeps after the configured time; check client sleep block and headset audio restore after Stop.
12. Test fresh install, upgrade, repair and uninstall on the actual platforms, including state retention and no damage to unrelated software.

There is no demonstrated universal latency threshold in current evidence. Each check counts when its result repeats; a short successful session alone is not enough. Results on hardware not listed under *Tested so far* are especially welcome (a bug report with both reports is the best way to send them).

## Windows headset PC

**No item in this list has been checked yet.** The Windows client has been built and tested only in code: the companion's unit tests, the native tests under Wine with a software Vulkan driver, the installer under Wine, and a smoke test of the companion and its page under Wine ([technical reference, §20.2](TECHNICAL_REFERENCE.md#202-built-and-tested-in-code-not-yet-confirmed-on-hardware)). Its decoding on a real GPU, Windows Firewall, Wi-Fi and power settings, Baballonia's Windows installer and SteamVR on Windows have never run.

You need a headset PC with Windows 10 or 11 (64-bit), Steam and SteamVR, and the headset working in SteamVR on it (start SteamVR once with the headset connected, finish its room setup, then close it), and a rendering PC with VROSTBridge Host 1.0.0.14. The client's log is `client-latest.log` in `%LOCALAPPDATA%\VROSTBridge` (Start menu: *Client startup logs*); its report has the same lines. Send reports from both PCs with each result.

Record for each Windows run, as well as the items under *Record each run*: the Windows edition, version and build; the headset PC's GPU and its driver version (and which GPU drives the headset if there are two); the client's `STATUS SteamVR's GPU for D3D11VA` and `STATUS Video decoding` lines; whether the PC was on its charger; Wi-Fi or Ethernet.

1. Run `VROSTBridge-Client-Setup-1.0.0.14.exe`. It is not code-signed, so Windows SmartScreen may say *Windows protected your PC*: choose **More info → Run anyway**, and record whether it asked. It passes when it installs without an administrator prompt into `%LOCALAPPDATA%\VROSTBridge\Client\1.0.0.14`, the Start menu has *VROSTBridge Client*, the page shows *VROSTBridge Client 1.0.0.14*, and running the setup again (a repair) keeps settings and pairing. `VROSTBridge-Client-Portable-1.0.0.14.zip`, unpacked whole, opens the same page from its `VROSTBridge Client.exe`. On a PC where SteamVR has never run, if you have one, Start must stop with *SteamVR is not set up on this PC yet*.
2. Press **Allow home-network connection** and accept the one administrator (UAC) prompt. It passes when the page's card then reads *Home-network firewall rules are in place (local subnet only)*, and Windows Defender Firewall's inbound rules hold exactly five `VROSTBridge.Client.* (home network)` rules, each for every network profile and the local subnet only: TCP 9943, UDP 9944 and UDP 5353 for `VROSTBridgeClient.exe`, and TCP 9945 and UDP 9944 and 9946 for the companion's `python.exe`. Declining the prompt must change nothing and say so.
3. Discovery and pairing: with *Allow home-network clients* on in the host page, start a session on the client. It passes when the client finds the host by itself, without an address typed, pairs, and the host page lists it; the next Start reuses the pairing.
4. D3D11VA decoding on SteamVR's GPU: with *CPU decoding* off, start a session. It passes when the client's log has `STATUS SteamVR's GPU for D3D11VA: <GPU> (DXGI adapter <n>); decoder profiles h264=… hevc=… hevc_main10=… av1=… av1_10bit=…`, then `STATUS Video decoding: D3D11VA on <GPU>, copied to Vulkan` and `STATUS Video decoder opened successfully: backend=D3D11VA …`, all naming the GPU the headset is connected to (on a PC with two GPUs, the one SteamVR renders with), the page's video details say *decoded with D3D11VA*, and the picture in the headset is right. The adapter is matched by its LUID, which the log does not print: its name and DXGI number identify it. Record the decoder profiles line. `STATUS SteamVR's GPU for D3D11VA not found`, `STATUS Video decoding: D3D11VA unavailable` or a `FATAL` D3D11VA line is a failure. Then turn on *CPU decoding* and start an H.264 or HEVC session: the log must say `STATUS Video decoding: CPU, uploaded to Vulkan` and the picture must be right (without foveation); record its frame rate, as CPU decoding is a troubleshooting fallback.
5. Codecs and 10-bit: the client offers the host only what this GPU's decoder handles (`STATUS Stream features offered: foveated=… ten_bit=… av1=…`). Stream H.264 (at *Standard*), HEVC and, where offered, AV1 and 10-bit colour, a few minutes each. It passes when every offered combination gives a correct picture: the `VIDEO` line names the codec with `"decoder":"d3d11va"`, a 10-bit stream's `VIDEO_COLOUR` line says `"bits":10`, blacks are black and nothing is corrupted. Choosing AV1 where the line says `av1=0` must give an HEVC stream from the host, not a broken one.
6. The copy's cost: at the size you would use, run the same scene for five minutes with foveation *Off* and again with *Balanced* (or *Eye-tracked* on a Beyond 2e). For both runs record, from the client's TIMING lines, `map_sync_import_mean_ms`, `map_sync_import_p95_ms` and `map_sync_import_max_ms` (the copy of each picture into Vulkan), `unique_fps` against `refresh_hz`, and the lost frames. It passes when the stream holds the headset's refresh rate (`unique_fps` at `refresh_hz`) at that size. A copy whose p95 takes a large part of the frame interval (13.3 ms at 75 Hz), or a frame rate clearly higher with foveation than without, is the evidence for sharing the picture without the copy.
7. The frame pass: one shader serves every GPU (its constants in a uniform buffer, none as push constants, so a driver with only the minimum push-constant space runs it too). The log must say `STATUS Fused frame pass ready: …` and `STATUS Frame pass: fused (one pass per shown frame); sharpening …`, and `STATUS GPU time stamps: on (…)` where the GPU's queue has time stamps. It passes when the picture, its sharpening and the re-aim are right and the `TIMING` lines carry `frame_pass_gpu` and `plane_copy_gpu`; record both with item 6's numbers.
8. Re-aim and controllers: on the Windows PC, do items 1, 3 and 4 of the *Required sequence* above (local SteamVR first, cold and warm Start/Stop, a 30-minute session with every control) and the page's alignment check. It passes when head turns keep head-locked text and held objects steady, both controllers' buttons, sticks, touches, finger poses, haptics and the host's menu work as on a Bazzite headset PC with the same headset, and both runtimes close on Stop. Record the alignment check's answer.
9. Audio: play game audio in a session (and speak, if *Headset microphone* is on). It passes when the sound plays where SteamVR's audio settings send it (the headset's own output, where it has one), with *Headset microphone* on the microphone reaches the rendering PC's virtual cable, and after Stop Windows' default devices are as before. VROSTBridge itself changes no audio device on Windows; the page names the current defaults.
10. Tray: with the page closed, start a session from the tray icon's **Start session** and stop it with **Stop session**. It passes when both work, the tooltip shows the session's state, and Windows shows a *Streaming* notification once the picture arrives. A tray-started session that ends on its own (end `VROSTBridgeClient.exe` in Task Manager, for example) must show *Session stopped* with the reason, and one that cannot start (rendering PC off) *Session did not start* with the reason.
11. Start at sign-in: turn on *Start VROSTBridge Client when I sign in* (in the installer or on the page), then sign out and in. It passes when only the tray icon appears (no browser, no SteamVR) and a session starts from it; with the switch off it no longer starts at sign-in. If Windows' own *Startup apps* setting has turned it off, the page must say so.
12. Wi-Fi: on Wi-Fi, run a session of at least 15 minutes. It passes when the client's log has `WIFI … Media streaming mode is on for this session` and `WIFI ROAMING locked: Wi-Fi background scans are off for this session`, the timeline shows no stall every few minutes, and after Stop the log says *Wi-Fi media streaming mode ended* and *Wi-Fi background scans are back on*, with any other Wi-Fi adapter on the same network reconnected. On Windows 11 24H2 or later, with location access for desktop apps off, the page must show *Windows didn’t allow reading the Wi-Fi network name; roaming detection is off* while the session streams normally.
13. Power: set Windows' power mode (Settings → System → Power & battery) to anything but *Best performance*, and note your power plan. It passes when the mode reads *Best performance* during a session, the PC and its display stay on through a long session without keyboard or mouse use, and your own mode is back after Stop. Then force a crash: during a session, end VROSTBridge Client's process tree in Task Manager (close SteamVR too if it stays open) and start VROSTBridge Client again. It passes when your mode comes back at that start, with the log line `POWER recovered: Windows' power mode is back to …`. With the High or Ultimate performance plan the mode must be left alone.
14. Baballonia's Windows installation: close Bigscreen's own eye-tracking app, turn on *Eye tracking* and set up Baballonia, accepting its licence. It passes when about 423 MB downloads, the size and SHA-256 check passes, it installs without a window into `%LOCALAPPDATA%\VROSTBridge\Baballonia\1.1.1.0rc6`, no Baballonia window opens by itself when it finishes, no new Baballonia shortcut appears in the Start menu or on the desktop, and *Installed apps* (*Apps & features* on Windows 10) gains no Baballonia entry (one you had before stays as it was). Record how long it took.
15. Your own Baballonia: on a PC where Baballonia 1.1.1.0rc6 was installed with Project Babble's own installer, set up eye tracking. It passes when VROSTBridge uses that installation without downloading (the client's log says *Eye tracking: the Baballonia 1.1.1.0rc6 installed on this PC (…) is used; nothing was downloaded*), and both *Remove Baballonia* and uninstalling VROSTBridge Client leave it installed and working. Another Baballonia version must not be used: VROSTBridge downloads its own instead.
16. Calibration and gaze: start a session with *Eye tracking* on, choose **Show Baballonia** and run its *Eye* calibration, turning your head far enough each way (corners too) while you follow the dot. It passes when the eye camera is found (Windows normally names it `BigEye`; under another name, such as *USB Video Device*, the page and the log say how to fix that), the calibration shows in the headset over the stream, the session keeps running through calibration and training, the card shows 30 or more eye-tracking samples a second, the sharp region follows your eyes toward the edges, and *Gaze reach* then has no direction under 30°. Record the four *Gaze reach* numbers and the samples a second.
17. Stop: press **Stop** on the page. It passes when the native client stops within 8 s (`STATUS Client stopped by the companion` in the log), the log has `Requesting local SteamVR shutdown.` and then `Local SteamVR stopped.`, the host returns to waiting, and the power mode and Wi-Fi are back as before; SteamVR started on its own afterwards shows its home and dashboard again. `Local SteamVR did not stop; closing only verified session processes.` means SteamVR ignored its quit request: record it.
18. A compositor failure: during a session, end `vrcompositor.exe` in Task Manager. It passes when the log says *SteamVR's compositor on this PC closed unexpectedly*, the session restarts by itself, once (a second failure within ten minutes stops it with an explanation), and the log and report have `STEAMVR crash detail:` lines; a process ended this way leaves no crash record, so the line saying Windows recorded none is the expected one here.
19. Uninstall: uninstall VROSTBridge Client (from *Installed apps*, *Apps & features* on Windows 10, or its Start menu entry). It passes when Windows asks once for administrator permission to remove the firewall rules, no `VROSTBridge.Client.*` rule remains, the Run value `VROSTBridgeClient` is gone (*Startup apps* no longer lists VROSTBridge Client), the program folder and its Start menu entries are gone, settings, pairing and logs stay in `%LOCALAPPDATA%\VROSTBridge`, Baballonia is kept unless you chose to remove it, and a VROSTBridge Host on the same PC is untouched. Declining the administrator prompt must leave VROSTBridge Client installed, with a message saying why.

As above, each check counts when its result repeats; for anything that fails, send both PCs' reports and say at which step and which log line it failed.
