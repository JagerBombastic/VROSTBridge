## A. Since 1.0.0-rc4.5 (developed as RC4.6, never released under that number)

Functional changes from the first RC4.5 test with the Beyond 2e: Baballonia's calibration showed nothing in the headset with no SteamVR running, showed each eye the other eye's picture with SteamVR started by hand, and ended the session when started during one (the client log said *Local SteamVR requested this client to quit*). Also Baballonia's window covered the page, and opening the page again opened another browser tab.
- **Calibration over the stream** (`launcher/baballonia.py`): `prepare_calibration()` (at session start, and idempotent) puts `CALIBRATION_LAUNCHER`, a POSIX shell script, where Baballonia starts its calibration program (`Calibration/Linux/Overlay/BabbleCalibration.x86_64`) and keeps Baballonia's program beside it as `BabbleCalibration.program`. While SteamVR runs, the launcher adds Baballonia's own `--use-openvr`: the calibration becomes a SteamVR overlay over the stream instead of an OpenXR scene application, which made SteamVR ask the client to quit. Without SteamVR everything is passed on unchanged. `VROSTBRIDGE_CALIBRATION=openxr` in the companion's environment keeps Baballonia's way, and only then is `XR_RUNTIME_JSON` set to SteamVR's `steamxr_linux64.json`. *Remove Baballonia* deletes both files.
- **Baballonia minimised** (`launcher/x11_window.py`, libX11 through ctypes): for a Desktop Mode session Baballonia's window is iconified once it appears; *Show Baballonia* (action `eye-show`) brings it back and it is not minimised again in that session. One process-wide X error handler, installed once, so an X error from a window that closed at the wrong moment cannot stop the companion. The frozen companion bundles no X11 libraries (`packaging/VROSTBridge-Client.spec`).
- **One page tab** (`launcher/desktop.html`): a `BroadcastChannel` makes an older tab close itself when a newer one opens (or say it is open in a newer tab); the pages use fixed local ports, 9947 (client) and 9948 (host), or any free port when taken (`PAGE_PORTS` in `launcher/app.py`).
- **Guidance**: the *Eye tracking* card and Game Mode name Baballonia's four calibrations, say where a calibration would show, and say to keep the session running while it trains.
- **Publishing**: MIT `LICENSE` (JagerBombastic), `NOTICE`, `THIRD_PARTY.md` and the missing licence texts in `licenses/`; the eye-camera helper's own MJPEG server (`third_party/go-bsb-cams/mjpeg_stream.go`) instead of a module without a stated licence; test data without real addresses or serials; `CONTRIBUTING.md`, `SECURITY.md`, issue templates and a checks workflow in `.github/`; `scripts/package_public_source.py` and [PUBLISHING.md](PUBLISHING.md).

## D. The calibration overlay's Vulkan layer (1.0.0.2)

From the 1.0.0.1 test on Bazzite: choosing *Eye* in Baballonia showed the calibration window for a moment, then it closed, with nothing in the headset, in a session and with SteamVR alone; Baballonia's calibration buttons then stayed greyed out. The crash dumps (`coredumpctl`) showed `BabbleCalibration.program` killed by SIGSEGV at address 0, called from SteamVR's `vrclient.so` inside `IVROverlay::SetOverlayTexture`, from godot-openvr's `OpenVROverlayContainer::draw_overlay`. SteamVR shares an overlay's Vulkan picture with its compositor through extension commands on the program's own device; Godot 4.5 enables `VK_KHR_external_memory_fd` but not `VK_KHR_external_semaphore_fd` (nor the KHR timeline names), Mesa's `vkGetDeviceProcAddr` returns NULL for commands of extensions not enabled (Windows drivers return them), and `vrclient.so` calls the NULL. Baballonia waits for the dead calibration (its overlay connection closed), hence the greyed-out buttons. Up to RC4.5 the calibration ran through OpenXR as its own SteamVR application and did not take this path (it ended the stream instead). SteamVR Room Setup fails on Fedora's Mesa the same way ([steamvr-room-setup-on-fedora](https://github.com/rcannood/steamvr-room-setup-on-fedora), whose analysis matched ours and whose extension list the layer uses; no code taken).
- **Layer** (`client/platform/linux/openvr_texture_layer.c`, manifest `VkLayer_vrostbridge_openvr.json`, layer `VK_LAYER_VROSTBRIDGE_openvr_textures`, loader interface 2, libc only): at `vkCreateInstance` it adds the four external-capability instance extensions (core in 1.1; the loader passes each driver only those it offers); at `vkCreateDevice` the external memory, semaphore and fence extensions with their fd forms, dedicated allocation, memory requirements 2, bind memory 2, image format list, dma-buf, foreign queue family, DRM format modifiers, timeline semaphores and synchronization2, each only where the driver offers it and the program did not ask for it, and the `timelineSemaphore` and `synchronization2` features where supported and not already set by the program (alone or in its Vulkan 1.2/1.3 feature structure). If the driver refuses the longer list it retries with the program's own. One stderr line per device names what it added and any command SteamVR calls that is still missing (Baballonia's log, in client reports).
- **Launcher** (`CALIBRATION_LAUNCHER` in `launcher/baballonia.py`): when the program starts with `--use-openvr` (the launcher's own change from `--xr-mode`, or Baballonia's), it sets `VK_ADD_LAYER_PATH` to `vrostbridge-vulkan` beside it and `VK_INSTANCE_LAYERS` (both ahead of any the user set), only if the manifest is there and `VROSTBRIDGE_VULKAN_LAYER` is not `off`. `prepare_vulkan_layer()` copies the layer from the installation's `vulkan/` (CMake installs it there) into that folder whenever it differs, manifest last; a failed copy is logged and the calibration starts without it, as in 1.0.0.1.
- **Checks**: CTest `openvr_texture_layer` (`tests/vulkan_layer_tests.cpp`: a device made as Godot makes it, with the layer, has every command SteamVR calls whose extension the driver offers, and a timeline semaphore works); `tests/test_vrostbridge_1002.py` (the version, the launcher's environment in each case, the copy and its updates, the manifest against the exports, and the real layer reaching a Vulkan program through the real launcher). Baballonia's real calibration program ran with the layer on lavapipe and drew as without it; on SwiftShader, which like the test PC's driver offers `VK_KHR_external_semaphore_fd`, a Godot-style device has every command SteamVR calls with the layer and lacks the semaphore ones without it.

## E. From the 1.0.0.2 test (1.0.0.3)

The 1.0.0.2 test confirmed the calibration in Desktop Mode and the eye-tracked foveated stream, and found six problems (two reports, client and host, plus the maintainer's notes); the maintainer also asked for the logo's lettering in the header:
- **Game Mode reservation** (`launcher/game_mode.py` `gamescope_alive`): the lease record's owner was checked through `process_identity`, which reads `/proc/PID/exe`. Bazzite's gamescope (Terra's `terra-gamescope`, `%caps(cap_sys_nice=eip)`) is non-dumpable once started, so that link is refused (EACCES) even to the same user, and every Game Mode start looked stale. The check now reads `stat` (start time), `status` (real and effective UID) and `cmdline` (gamescope with the leased connector), and checks the program link only where it can be read. `tests/test_vrostbridge_1003.py` reproduces the capability case with a program given `cap_sys_nice=eip` and run as another user.
- **Host SteamVR ownership** (`host/control.py` `_adopt_new_servers`): a second vrserver appeared 3 s after a 61.9 s start. The monitor ended the session and every Stop refused to close SteamVR. A new vrserver from the session's own SteamVR installation, created after the launch, now joins the session while one of the session's processes still runs or while the monitor waits out a loss. *Interrupted* is logged only for a runtime that was ready or whose server exited (`lost_since`, `loss_pending`), and a slow start is explained once after `SLOW_START_S`. Reports gain `vrserver.previous.txt` and `vrmonitor.txt` (`launcher/diagnostics.py`), and a refused client report (HTTP 403) is said once.
- **Reduced area**: driver patch `0016-host-foveation-prefilter.patch` (composition mip chain with `GenerateMips` each frame, an anisotropic clamped sampler for the compression pass, the previous sampler restored, fallback without mips, log line `VROST_FOVEATION_PREFILTER`). Client `fused.comp`: an exact four-tap B-spline (`lumaBSpline`) where an output pixel spans half a texel or less, Catmull-Rom from one texel, blended between. The CPU model and CTest `fused_shader_contracts` (test 6) measure motion change and overshoot.
- **Eye-tracking speed**: the camera helper's `mjpeg_stream.go` sends each reader the newest picture it does not have yet, at most one every 15 ms (was one per 50 ms, effectively 17 a second). Baballonia's One Euro eye filter is set once from 0.5 Hz/3 to 1 Hz/10 while unchanged (`EYE_FILTER` in `launcher/baballonia.py`); the test simulates Baballonia's filter for lag and jitter.
- **Eye-tracking view**: FOVEA lines 30 a second (`client/platform/linux/main.cpp`), the page polls 20 a second and draws at the screen's rate with gliding, a one-second trail and resolution squares (`launcher/desktop.html`), the host page gets 10 a second (`share_fovea`), Game Mode redraws 20 a second with batched squares (`SDL_RenderFillRects`). A gaze that holds still keeps its trail point fresh, so the trail starts where the eye was when it moves on; the trail ends at the dot as drawn and fades by the age of each stretch's older end (Game Mode draws it as a line of dots).
- **Header wordmark**: `brand/tools/vrostbridge_symbol.py` `wordmark_inline()` puts the traced VROST and *Bridge* (`brand/tools/set_bridge.py`: Montserrat 400 outlines, positions from HarfBuzz through Pillow's raqm layout) on one line; `scripts/build_brand_assets.py` writes `launcher/brand/vrostbridge-name.svg` (page) and `.png` (Game Mode, placed by `NAME_CAP` and `NAME_CAP_TOP`). Every other artwork file came out byte-identical when rebuilt.
- **Baballonia across updates**: `release` is now the pinned release once set up, else an earlier VROSTBridge's (kept until *update*), `adopt_earlier_copy()` moves a copy an installation before 1.0.0.1 left under another folder name, `eye-status` gives the installer's last line, and the uninstaller asks (Keep default, Remove, Cancel; `--keep-eye-tracking`).

## F. From the 1.0.0.3 test (1.0.0.4)

The 1.0.0.3 test (two client sessions in one report, the host's report, and the maintainer's notes): moment-to-moment tracking felt good, but the coarse area at the edge could be looked at directly, there were short lags between good moments, Beat Saber stuttered and turned grey at times, High resolution with eye-tracked foveation struggled, and Game Mode's D-pad and stick did not go where expected. Every fix is general: thresholds come from the PC's own reported clocks, the network path's own measurements, or the stream's own timing, never from the test hardware.
- **Gaze hold on the host** (driver patch `0017-host-gaze-hold.patch`): the host's foveation put the sharp region back in the optical centre as soon as its gaze sample was 150 ms old, which happened for 39 % of the frames in both sessions (blinks and the eye tracker skipping pictures; one pause lasted 20 s). `vrostbridge_foveation.rs` now keeps the last region for `gaze_hold_ms` (stream options, default 1000, at most 5000) beyond the stale time and then returns it to the centre; the log line `VROST_GAZE_FOVEATION` adds `held_frames`, `pauses`, `longest_pause_ms` and `returns`. The companion writes `gaze_hold_ms` only when the driver's build manifest lists the patch (`host/stream_options.py`, feature `gaze-hold`). `scripts/host_module_tests.py` builds the two Rust modules with stand-ins for the ALVR types they use and runs their tests on Linux (10 pass).
- **Power balance** (`launcher/power_balance.py`): in the second session every processor core ran at about 540 MHz, below its own 1100 MHz minimum, because the GPU clock was fixed at its maximum under a 28 W limit; Baballonia fell from 54 to 12 samples a second and the stream's own work stalled every few seconds. `CpuClocks` reads the performance monitor's samples and reports a processor below 75 % of its own `scaling_min_freq` in two samples running (about 10 s), with the cause `fixed-gpu-clock` (steamos-manager's level `manual`, or a clock at 90 % of the GPU's own maximum or more while under 60 % busy) or `power-limit`. `advice()` words it, with a suggested fixed clock of 60–75 % of the GPU's own maximum. `SteamOSPower` reads steamos-manager's `GpuPerformanceLevel1` and `TdpLimit1` on the session bus (`busctl --user`, every 30 s) and sets `GpuPerformanceLevel` to `auto` only when the person chooses *Set the GPU clock to automatic* (action `gpu-auto`, page and Game Mode). Shown on the session card, the client page, Game Mode, once in the headset (`notice`), and logged as `POWER_BALANCE`. Baballonia now runs under `nice -n 5` (`launcher/baballonia.py`), so the stream's own work goes first when the processor is short.
- **Pacing** (`launcher/network_test.py`, `launcher/link_test.py`): wired frames were paced at 92 % of the link speed (920 Mbit/s on a USB Ethernet adapter whose test lost 12 % at 750 Mbit/s); one frame was lost every 3 s or so, each costing a keyframe and three or four frames. The test records `lossless_mbps`, the highest step before the first lossy one (none when no step lost anything: the link speed decides), and wired pacing stays at or below it; `path_tested()` tells a 1.0.0.4 test from an earlier one. A wired path whose saved test predates it is tested again once. Without a test, a USB adapter (`/sys/class/net/<if>/device` under a USB bus) is paced at 60 % of its link speed. The test itself still runs at the full pace.
- **Frame hold** (`core/stream.hpp`): a frame up to 1 s old (was 250 ms) stays up, re-aimed to the head, before the grey recovery view; the *Waiting for video* card still shows at 0.5 s. CTest `stream_contracts` covers both limits.
- **Game Mode controls** (`launcher/game_ui.py`): left and right change a settings row's value (`adjust()`: previous or next value; switches off or on) instead of moving focus to *Back*; rows scrolled out of view are reached only by stepping through the list, and lists stop at their ends. Held directions repeat (`REPEAT_DELAY_S` .38 s, then every `REPEAT_S` .11 s; the stick every `STICK_REPEAT_S` .14 s); the stick moves past `STICK_ON` and releases below `STICK_OFF`; one press reported by two sources within `DUPLICATE_S` moves once; controllers are opened once and kept.
- **Diagnostics**: `launcher/timeline.py` keeps one row per 10 s for the whole session (360 rows, then the first half hour and the latest) in client reports: frame rate, losses, keyframes, stalls, grey frames, gaze samples a second, the host's gaze, held and centred frames, clocks, load, power, temperature, and the processor time of the session's own programs (`launcher/performance_monitor.py` `PROCESS_GROUPS`; anything else is summed as *other*). The gaze relay counts the pauses between samples by length (`launcher/gaze_provider.py` `GAP_BANDS`). Counts only; where the user looks is never logged.
- **Checks**: `tests/test_vrostbridge_1004.py` (the version, the hold's options and log keys, the power balance on processors with different minimums and GPUs with different maximums, pacing, the timeline, process groups, gaze pauses, Game Mode navigation and repeat, the pages); CTest `stream_contracts`; the driver modules' Rust tests.

## G. From the 1.0.0.4 test (1.0.0.5)

The 1.0.0.4 test (client and host reports from several sessions, and the maintainer's notes): High looked and tracked reasonably well; blacks were dark grey on the Beyond's OLED panels with 10-bit colour on and black with it off; eye tracking seemed to lag and did not always register where the eyes looked, and the sharp region could be seen moving; Ultra still struggled; once no video arrived at all; and every session ran at 30 Mbit/s. Every fix is general: limits come from what the converter, the cameras, the PC or the network path report about themselves, never from the test hardware.
- **Exact colour on the AMD path** (driver patch `0018-host-exact-colour-and-pose-drops.patch`, `VROSTBridgeColor.h`, `VideoEncoderAMF`): with 10-bit on, the encoder got 10-bit RGB and converted it itself, producing studio-range samples (black at 64 of 1023) in a stream labelled full range. The host now converts to Y′CbCr with a stated profile (BT.709 full range), converts a 128 × 64 test picture (black, white, red and mid-grey stripes) with the same converter at the start of every stream, reads the samples back, classifies range and matrix (`Classify`; `tests/host_color_tests.cpp` builds the header from the patch and checks it against modelled converters, including the 1.0.0.4 fault), and labels the stream (H.264 `FULL_RANGE_COLOR`, HEVC `NOMINAL_RANGE`, the input and output profiles, AV1's) with what was measured. When the check fails or the encoder refuses the 10-bit settings it streams 8-bit. `VROST_COLOR`, `VROST_COLOR_FALLBACK`, `VROST_COLOR_RELABEL` and `VROST_COLOR_CONVERTER` lines; AV1's bitrate changes use AV1's properties. The client logs the colour its decoder reports (`vulkan.cpp` `colourLine`) and the page shows bit depth, range and the 8-bit note.
- **No picture without a head pose** (patch 0018, `vrostbridge_pose.rs`; `openvr_device.cpp`): the host renders only for a head pose the client sends; with SteamVR on the headset PC calibrating its tracking (result 101 in the report) every frame was dropped without a word. The host counts dropped and sent frames per 5 s window (`VROST_NO_HEAD_POSE`); the client counts head poses sent and missing, keeps SteamVR's tracking result (`HEAD_TRACKING` line, `head_*` metrics) and says *Headset not tracked* after 2 s (page, Game Mode, headset card); the host page says *Waiting for the headset’s position*.
- **Eye cameras** (`third_party/go-bsb-cams`: `main.go`, `jpeg_frames.go`, `camera_stats.go`, vendored go-uvc; `VROSTBRIDGE_CHANGES.md`): pictures passed on as the cameras sent them (checked by `cleanJPEG`, standard Huffman tables added where missing, the first five and one in 120 decoded in full; re-encoded only for an `FF D9` inside a header or over 900 KiB), the cameras' fastest frame interval (`ClaimFrameReaderAt`; upstream committed GET_MAX, the slowest), damaged pictures skipped (`ErrDamagedFrame`), reads bounded (`ErrTimeout`, also for a whole frame while USB data keeps coming), a clean reopen after 2 s without a picture with waits from 250 ms to 4 s, transfers of at most 32 packets, at most one picture per 8 ms per reader, `STATS` and `CAMERA` lines. In the 1.0.0.4 report the helper used a whole processor core and eye-tracking samples swung between 10 and 55 a second with pauses up to 10 s. The companion keeps the helper's lines (`launcher/eye_tracking.py` `helper_values`, `cameras.feed`), the timeline adds camera pictures a second, losses and re-openings, and the card names the camera rate. Go tests: 20, under the race detector.
- **Baballonia's filter** (`launcher/baballonia.py`, `EYE_FILTER_VERSION` 2): 2 Hz and speed 60 where the filter is still Baballonia's or 1.0.0.3's; 90 % of a 5 or 10 degree movement after 33 ms instead of 67–83 ms at 60 camera pictures a second (simulated with Baballonia's own filter).
- **Comfort zone** (driver patch `0019-host-gaze-comfort.patch`, `vrostbridge_foveation.rs` `movement_threshold`): the region moves only when the gaze leaves `gaze_comfort` × half the region's size around its middle (default 0.5, accepted 0 to 0.8, never less than the 2.5 % dead band); 0.85 moves a second instead of 3.17 in a simulated minute of gaze. The companion writes `gaze_comfort` only for a driver with the patch (feature `gaze-comfort`).
- **Ultra** (`core`/`client`: `shownEyeSize`, `video.hpp`): a stream larger than SteamVR's recommended size is shown at that size, scaled in the fused pass that already converts it (`STATUS` line, `shown_width`/`shown_height`, *shown at* on the page and in Game Mode); the graphics warning offers *Set the GPU clock to automatic* when the GPU is held at a fixed clock (`graphics_limit.advice(gpu_auto=…)`).
- **Network test** (`launcher/link_test.py`, `launcher/network_test.py`, `launcher/app.py` `ensure_network_test`): the 1.0.0.4 test on the USB adapter found no clean rate (three packets lost at 80 Mbit/s, frames that looked late from 150), so every session ran at 30 Mbit/s for the result's month. The receiver is a companion thread; datagrams waited for its turn. Now: kernel arrival times (`SO_TIMESTAMPNS`) and the socket's own drops (`SO_RXQ_OVFL`, `local_drops`, credited to the step they were sent in, `network_loss_pct` without them), a 0.5 ms thread switch interval while receiving, a warm-up step at the lowest rate (not judged), frames sent after the last one seen in a step without an end marker counted from the host's own count, the pace limit from steady loss (`CAPACITY_LOSS_PCT` 1 %), a wired automatic bitrate of at most 40 % of the pace (`SEND_FRACTION`, limit `latency`), and a result without a clean rate (or nothing received) tested again before the next session, up to three in a row (`needs_retest`), with an earlier clean result that is still young enough kept meanwhile. Saved results keep their steps and the receiver's timing.
- **Review**: an independent review of the camera helper, patch 0018 and the network test found five defects, all fixed before release: a frame read that never returned while USB data kept coming without a frame, drops at a step's end credited to the next step (hiding its network loss), a libusb context kept for every unplug, a crash on a malformed USB packet header, and an earlier network result kept although too old to be used.

- **Decisions.**
  - *The copy first.* FFmpeg cannot map a Direct3D 11 picture into Vulkan. Downloading it into the staging buffer keeps the Bazzite frame pass unchanged, works on any GPU with Direct3D 11 video decoding, and could be tested here (the plane upload and the pass on lavapipe under Wine). Sharing the decoder's texture with Vulkan, or decoding with Vulkan Video, would avoid the copy, but only hardware can show whether that is needed and works, so the copy is timed (`map_sync_import`) and zero-copy waits for reports. Its size: a Beyond's Standard stream (4032 × 2016 before foveation) is about 12 MB a picture in 8-bit, each way, twice that in 10-bit, under 4 MB with the eye-tracked default.
  - *Loopback UDP for the gaze.* Windows has no Unix datagram sockets, and Python on Windows no AF_UNIX at all. The relay sends the same `VRG1` datagrams to a UDP port on 127.0.0.1 chosen free at each Start, which the native client binds on 127.0.0.1 with `SO_EXCLUSIVEADDRUSE`, so no other program can read or inject samples; `gaze_target()` refuses any target off this PC. The datagrams are stamped with `time.monotonic_ns()`, which with the embedded Python 3.13 is the native client's own clock on Windows.
  - *`quit` on standard input.* Windows has no SIGTERM, and ending the process skips the native client's clean-up (SteamVR's scene application, the transport). The client already read commands on its standard input, so `quit` joined them, on both systems; closing the pipe is the second way and ending the process the last (`quit_native()` in `app.py`, 8 s). Bazzite keeps SIGTERM.
  - *A firewall no wider than Bazzite's.* The rules open exactly the Bazzite client's ports, each only for the program that listens on it (the native client: TCP 9943, UDP 9944, UDP 5353; the companion's Python: TCP 9945, UDP 9944 for the network test and UDP 9946 for discovery replies; TCP 9946 is the host's broker, never the client's), rather than ranges on both protocols. Private profile and local subnet only, one UAC prompt, and ownership-marked names (`VROSTBridge.Client.*`) that never touch the host's rules on a PC with both.
  - *Baballonia kept private, or the user's own.* Project Babble publishes Baballonia for Windows only as an NSIS installer, which registers an uninstall entry, adds Start menu and desktop shortcuts and starts Baballonia when it finishes. As on Bazzite, VROSTBridge keeps its download private and removable: the installer runs silently into VROSTBridge's folder in a one-process job object, and its uninstall entry and shortcuts are put back as they were. Removal deletes that folder rather than running Baballonia's uninstaller, whose question about deleting `%APPDATA%\ProjectBabble` has no silent answer. A Baballonia the user installed, of the pinned version with matching files, is used instead of a second download and never removed. Its eye model is set to the processor once, because the stream's decoding and SteamVR's compositor need the GPU on time; a later choice in Baballonia is kept.
  - *Game Mode stays with Bazzite.* Game Mode is Bazzite's Steam session under gamescope; on Windows SteamVR drives the headset itself (no display lease) and the desktop is the session, so the companion lives in the tray, with sign-in start and notifications. The Game Mode and Steam-entry actions and `--game-mode` are refused on Windows with a plain message, there is no display lease, and Bazzite's other Linux parts (the camera helper, the calibration launcher and its Vulkan layer, the reprojection repair, steamos-manager's GPU clock) are hidden from its page.
  - *Settings put back.* Every Windows setting a session changes ends with it or has a receipt: media streaming mode and background scanning end with VROSTBridge's own Wi-Fi handle (at Stop, or when the companion exits); paused adapters and the power mode have receipts (`paused-wifi.json`, `session-power.json`) that the next start acts on after a crash. What closing the lid does is a machine-wide power-plan setting and is left alone: a PC left unable to sleep in a bag could overheat. Wi-Fi power saving is a power-plan setting on Windows, so it is changed only on request (*Turn off Wi-Fi power saving*), and then for every network.
- **Checks.** Python, all with stand-ins for the Windows calls: `tests/test_windows_network.py` (92), `test_windows_power.py` (44), `test_windows_runtime.py` (32), `test_windows_eye_tracking.py` (48), `test_windows_ui.py` (23), `test_windows_packaging.py` (24) and `test_vrostbridge_1007.py` (13 of its own, plus the session-lifecycle tests again in the client role on Windows: the version in every program, FFmpeg's Windows build against its notes, the tray's notifications, no Game Mode, gaze over loopback UDP, `quit`, crash records, the platform in reports, a PC without SteamVR, long paths wrapping); `tests/test_desktop_ui.js` with Windows fixtures.   - D3D11VA on real GPUs: the LUID match, FFmpeg's Vulkan device created with SteamVR's extensions on Windows, explicit frame timing with Vulkan submits, and the client's own upload code (`uploadPlanes()`), which the tests reach only through the shared helpers and the shaders.

## K. From the 1.0.0.8 test (1.0.0.9)

The 1.0.0.8 test was much better for motion and picture, with a few short stutters. The game audio lagged, broke up and crackled at times. The stutters were mostly lost frames, which also took the governor down from 65 to 40 Mbit/s. Frames sometimes arrived two or three at once, and one of two base stations was not woken (`le-connection-abort-by-local`). The host's list of received reports held 12 of up to 20.

The audio causes were all in ALVR's pinned audio code, at both ends:
- **Clients:** cpal's ALSA default is 44.1 kHz whenever the device's range includes it, as PipeWire's does, against a 48 kHz stream. rodio's converter does not filter when downsampling. ALVR's receive loop cleared the buffer on every loss and trimmed it only at twice the target, so clock drift swung between those edges. The device buffer was cpal's default (100 ms through ALSA).
- **Host:** cpal hides WASAPI's packet flags (`SILENT`, `DATA_DISCONTINUITY`). Loopback sends nothing while nothing plays. The thread ran at normal priority, and the 6-channel downmix lacked front left.

What changed:
- **Packet repair** (patch 0021; `alvr/sockets/src/vrostbridge_fec.rs`, `stream_socket/udp.rs`): XOR parity per interleaved group, sent on stream ID | 0x8000, which an older receiver drops as an unknown stream. Video parity is paced with its frame; audio is not paced. The host companion sets `fec_video_group` 10 and `fec_audio_group` 1 in `vrostbridge-stream.json` when the driver's manifest lists patch 0021 (`host/stream_options.py` `PATCH_FEATURES` → `parity`). The client counts what it rebuilt (`net_fec_video`, `net_fec_video_total` on `TIMING`; the page's *Rebuilt on the way*; `repaired` in the timeline).
- **Game-audio player** (patch 0022; `alvr/audio/src/vrostbridge_playback.rs`, `JitterPlayer`): the device at the stream's rate when offered (else a windowed-sinc converter, Blackman-Harris, 24 taps a side, 256 phases), a 40 ms device buffer, a drift correction of at most ±0.5 % on the smoothed level, a 2.5 ms cross-fade over a loss, and on underrun a fade with the target +10 ms (≤ 150 ms, −5 ms per calm minute). A gap of 300 ms or more counts as a pause. Its `VROST_AUDIO_OUTPUT` line is info-level, which the client's Rust log filter (errors only unless `RUST_LOG` says otherwise, and the host's *client log report level* while streaming) does not print, so the state travels through `vrost_audio_stats` in the transport: `audio_*` on `TIMING`, the page's *Game audio* line (`Application.game_audio_status`) and the timeline's `audio_dropouts` and `audio_lost` (gaps bridged).
- **Game-audio capture** (patch 0023; `alvr/audio/src/vrostbridge_loopback.rs`, `LoopbackCapture`): event-driven WASAPI loopback with a polling fallback, `SILENT` as zeros, discontinuities counted, MMCSS *Pro Audio*, a silent keep-alive render stream, F32/I16/I24/I32 mixes folded to stereo by channel mask with a soft limit (knee 0.9). It refuses a mix rate other than the stream's, and the server then falls back to cpal (`VROST_AUDIO_CAPTURE fallback=cpal`). The pinned 6-channel downmix gains front left. The driver's manifest feature is `audio-capture`.
- **Companion:** Baballonia's user service runs with `CPUWeight=25` (`launcher/baballonia.py`), since niceness does not reach across cgroups. Base stations get one retry after 1 s on both clients (`launcher/base_stations.py`, `BaseStations.ps1`), and BlueZ now reaches them one at a time as the Windows script already did. The host keeps `KEEP_RECEIVED = 3` reports and prunes at start (`launcher/reporting.py` `ReceivedReports.prune`).
- **Checks.** `tests/test_vrostbridge_1009.py`, the page checks in `tests/test_desktop_ui.js`, `cargo test -p alvr_sockets -p alvr_audio` in the patched checkout, and the host module tests for the new stream options.
- **Open risks.** The loopback capture on real Windows audio drivers (exclusive-mode devices, devices whose mix rate differs from the stream's), a client sound device that offers neither 48 kHz nor a fixed buffer, the 40 ms device buffer on Windows (it may add delay there, where the default was WASAPI's minimum), and the cost of parity on a link that was already near its pace (about a tenth more video, and about 2.3 Mbit/s for the audio's second copy).

## L. From the 1.0.0.9 test (1.0.0.10)

The 1.0.0.9 test was one session of 23 minutes on Wi-Fi. The game audio was clean: the host captured without gaps (`VROST_AUDIO_CAPTURE` max gap about 12 ms) and the client played at the stream's rate without conversion. No video frame was lost, and 48 were rebuilt from parity. Every audio dropout (12) and nearly every stutter fell on a pause of the Wi-Fi link: 18 arrival gaps of 86 to 212 ms, most of them 90 to 100 ms, about one Wi-Fi beacon interval. NetworkManager had refused to turn power saving off for the session (`Can't reapply changes to '802-11-wireless.powersave'`). The governor went 40 → 30 → 35 → 40 → 30 → 25 → 20 Mbit/s, every step for uneven arrival, and at 20 the per-second `packet_interval_p95_ms` (15.5 to 19.6 ms) was no better than before. A few short dips were the host itself: SteamVR there logged `WaitForAcquire timed out` while games loaded, with `source_limited` cadence on the client.

Two problems were reported:
- **The menu button opened the host's menu only sometimes.** The client logged a loss of input focus of 213 ms (`DEBUG input_focus=0` … `=1`) exactly when the right controller's `system_presses` went from 10 to 11. The headset PC's SteamVR takes input focus while its system button is held (its quick recentre, a long-press binding of the dashboard), and `controllerActionsAvailable()` then released every control on the host. The press reached the host for one input tick (focus is sampled once per display frame, actions every few milliseconds) or not at all.
- **Game Mode did not start a session.** SteamVR started (the client ran `vrstartup.sh` with its lease environment), but its compositor failed six times in 34 s: `CHmdWindowSDL: Using Wayland`, `No support for wl_drm_lease`, `VRInitError_Compositor_CannotDRMLeaseDisplay` (496). The display adapter offers `wp_drm_lease_device_v1` on every connection (its libwayland roundtrip test), so the compositor reached another display server, most likely gamescope's. The report could not say more: the Game Mode companion's lines had scrolled out under the later Desktop session's, and nothing logged which display SteamVR's server had.

What changed:
- **System button** (`client/device/input_protocol.hpp` `SystemButtonLatch`, `SystemButtonEvents`, `holdThroughFocusLoss`; `client/device/openvr_device.cpp`): a press is forwarded for at least 120 ms and ends with a release seen with focus or reported by `VREvent_ButtonUnpress`; `VREvent_ButtonPress`/`Unpress` for `k_EButton_System` are kept per hand in one atomic word ((time << 1) | pressed) by the event loop and read by the tracking loop. While the button cannot be read the press ends after 120 ms as a tap, and a new press needs a seen release first. A press event is believed for 10 s at most, and not once it is 250 ms old while the focused action reads released. A loss of focus under 500 ms keeps every other control's last value (the refresh treats it as available); longer releases them as before. `SYSTEM_BUTTON hand=… held_ms=… focus=kept|lost unread=0|1` per press (`unread=1`: for a moment neither focus nor an event to read it by); `focus_losses`, `focus_brief` and `system_events` on `INPUT`, and per hand `system_presses`, `system_focus_lost` and `system_unread`.
- **Game Mode** (`client/platform/linux/lease.cpp`, `launcher/game_mode.py`, `launcher/client_runtime.py`, `launcher/app.py`): the adapter's socket is `$XDG_RUNTIME_DIR/vrostbridge-headset-<pid>` and `WAYLAND_DISPLAY` its plain name (it was an absolute path into a folder of its own); a stale socket of the user's with that name is replaced, anything else refused, and only the socket the helper made is removed. It prints `LEASE_CLIENT connected|bound pid=… program=…`. `runtime_launch_environment()` drops `GAMESCOPE_WAYLAND_DISPLAY` whenever the lease environment is used (the probe and `vrstartup.sh`). `ensure()` reads the compositor log since its mark each round (`compositor_findings`): its lines about the headset display are logged once, a lease failure raises at once on any desktop (`lease_failure_message`), and in Game Mode `/proc/<vrserver>/environ` is read for `WAYLAND_DISPLAY` and `GAMESCOPE_WAYLAND_DISPLAY` (`steamvr_display` in the runtime status). `GameModeStartLog` keeps the lines of the last Start in Game Mode, its outcome and the adapter's later lines in `game-mode-last-start.json`; reports carry it as `game_mode_last_start`.
- **Bitrate** (`launcher/stream_budget.py`): the governor keeps the current bitrate's per-second arrival spread (`packet_interval_p95_ms`, up to 60 s, cleared at each change). A step down for uneven arrival alone, with at least 20 s of that spread, is checked over 12 s after 6 s to settle: if the median spread is not at least 7 % lower than before, the step is undone and `arrival_bound` stops uneven arrival counting for the session. `source_limited` seconds do not count as uneven.
- **Base stations** (`launcher/base_stations.py`, `BaseStations.ps1`): three tries 2 s apart; on Linux a 2 s `bluetoothctl` search before each retry, and the signal strength `bluetoothctl` printed for a station not reached during those searches (BlueZ drops its `RSSI` property when a search ends) in its result (`signal_dbm`) and the message.
- **Checks.** `tests/test_vrostbridge_1010.py` and `tests/input_tests.cpp`. The adapter's new socket code is checked as source only: `tests/lease_protocol_tests.cpp` covers its protocol, not its `main()`.
- **Open risks.** Whether SteamVR's event for the system button reaches a scene application without input focus (if not, a press made entirely while focus is taken is still missed; `system_events` will show); the 500 ms grace holding a control the player let go of during it; and Game Mode, if SteamVR's server turns out to start without the client's environment (`steamvr_display` will say) or its compositor ignores `WAYLAND_DISPLAY` for the headset.

## M. A lighter picture on the headset PC (1.0.0.11)

The 1.0.0.8 test streamed 2560 per eye at 75 fps: SteamVR's GPU time per frame (`gpu_ms`, `m_flTotalRenderGpuMs`) had a median of 6.84 ms with its compositor's share (`compositor_gpu_ms`) at 2.45 ms, so about 4.4 ms of each 13.3 ms frame was the client's own GPU work (the frame pass and the plane copy), with the GPU 57 % busy. In the 1.0.0.9 test at 2016 per eye the same figures were 5.3 and 2.3 ms. With eye-tracked foveation the stream at 2560 decodes about as many pixels as Standard with fixed foveation (1408 × 1408 per eye against 1408 × 1344), so the client's pass, which grows with the shown size, was the part to make lighter for smaller GPUs.

What changed:
- **The frame pass** (`client/platform/linux/fused.comp`, `client/device/conversion.hpp` `FusedFrame`, `fusedAxis`, `fusedFrameConstants`, `client/platform/linux/vulkan.cpp` `submitFused`, `openFused`): RADV's ACO statistics on null devices (`RADV_FORCE_FAMILY` phoenix, vangogh, rembrandt; `VK_KHR_pipeline_executable_properties`), per path with the region and detail forced, showed the pass VALU-bound (periphery 232 VALU and 5 image samples per pixel, centre 254 and 10, the blend band 336 and 14, on phoenix), mostly the foveation inverse's per-pixel terms (about ten divisions per axis from uniform values, which RDNA2/3 work out per lane). The terms are now precomputed per eye, axis and region in double on the processor (each edge region as `r = sqrt(max(a m + b, 0))`, texel `= c r + d`; the centre linear; mirroring, texel scale and the eye's offset folded in; an edge ratio of 1 or an empty edge region leaves only the centre), and each eye is a workgroup layer (`gl_WorkGroupID.z`), so eye-dependent values are scalar. ACO's inverse-throughput estimate fell by 34–38 % on phoenix and 36–40 % on vangogh per path (VALU 232→150, 254→198, 336→252; VGPRs 48→32). A gather-based 4×4 neighbourhood for the centre was considered and left out: it trades image samples for arithmetic in a pass already bounded by arithmetic. Every constant now comes from a uniform buffer per output image (544 bytes, std140, written while the image is free); push constants and `fused-uniform.spv` are gone.
- **Visible spans** (`client/device/visible_area.hpp`, `OpenVRDevice::visibleArea()`): `GetHiddenAreaMesh(k_eHiddenAreaMesh_Inverse)` triangles and the outline of `ComputeDistortion` along the panel's edge (64 points a side, all three colours), each turned into a row's x-extent by its edges, intersected (after `alignMeshes`: the mesh's orientation is undocumented, so it is compared with the outline on a 128-square grid and flipped vertically when that leaves at least 2 % of the outline less out, and dropped when it leaves out over 40 % either way; a mesh without an outline gets its flipped copy added, so each row spans both orientations), widened by `visibleMargin()` (3 % of the larger side, at least 8 px) across and down; a share under 0.5 for either eye is taken for a fault. The spans (packed `first | end << 16`, both eyes) are written into each output image's storage buffer when the image is made; a new image, or one the re-aim pass filled, is cleared to opaque black before the fused pass (`needsClear`). `VISIBLE_AREA {json}` per output size; `STATUS Lens area` says whether pixels are skipped (only with the fused pass) and what `alignMeshes` did; `--full-frame` (*Skip what the lenses never show* off) keeps whole rows.
- **Showing smaller** (`launcher/output_scale.py`, `Decoder::setShownScale`, `scaledEyeSize`): see the release notes for the rule. A second counts as behind only with SteamVR's GPU time known (`gpu_ms`/`refresh_hz` at least 0.75); the settling seconds after a step are not added to the down window; a step up needs the median of the last `up_wait` seconds' known shares (at least half known) at or under 0.6. A step down within 30 s of a step up pins the size; within 300 s it counts a round trip and doubles `up_wait` (60, 120, 240, at most 480 s), and three round trips pin it. The companion sends `scale N` from `check_graphics_limit` (`send_output_scale`, under `scale_lock`, which the switch's handler also takes, and only if the size still stands; one not sent is queued again) and logs `SCALE …`; the native client applies it to `target_` in the conversion worker for the next decoded frame, so each surface keeps the size it was made at, and `shownWidth()` stays the unscaled size. *Keep the frame rate when this PC falls behind* is a live option; turning it off sends `scale 100`.
- **GPU timing**: a timestamp query pool of two per output image and one of two per copy slot (16 slots, handed out per surface), both written at `BOTTOM_OF_PIPE` around the dispatch and the copy (a `TOP_OF_PIPE` begin may be written before earlier work on the queue completes), read with availability when the image or surface is next used, scaled by `timestampPeriod` and masked to `timestampValidBits`; `frame_pass_gpu_*` and `plane_copy_gpu_*` on `TIMING`, `pass_gpu_ms`, `pass_gpu_max_ms`, `steamvr_gpu_ms` and `shown_scale` in the timeline.
- **Native**: `beyond-balanced` is labelled *Native* (`launcher/headset.py`); *Auto* still starts a Beyond at Standard.
- **Checks.** `tests/fused_shader_tests.cpp` (the pass against its CPU model with the new constants, the constants against the formula in double, the std140 offsets, visible spans in the pass), `tests/visible_area_tests.cpp`, `tests/shown_size_tests.cpp`, `tests/planar_upload_tests.cpp` and `tests/test_vrostbridge_1011.py`. New: `tests/video_pass_tests.cpp` runs `VulkanVideo` itself (open, `submitFused`, the spans and clears, the re-aim pass then the fused pass on one image, a smaller output, the time stamps) against a stand-in SteamVR generated from the OpenVR headers (`tests/make_openvr_stand_in.py`, `tests/openvr_stand_in.hpp`; `friend struct VideoTestAccess` fills a planar surface on Linux, where no VA-API decoder exists), and on Windows through `convert`/`uploadPlanes` with CPU-decoded frames under Wine; it fails if the re-aim pass stops marking its image for a clear. With the Khronos validation layer and synchronisation validation (`VK_INSTANCE_LAYERS`, `VK_LAYER_ENABLES`), it and the other Vulkan tests report nothing (a test-only readback offset in `planar_upload_tests.cpp` was aligned); a missing barrier after the clear shows as `SYNC-HAZARD-WRITE-AFTER-WRITE`, so the check bites. On lavapipe the new pass ran about a fifth faster than 1.0.0.10's in alternating runs (CPU-emulated, so relative only).
- **Open risks.** The real gain on GPUs (until the reports' `frame_pass_gpu`); headset drivers without a visible-area mesh or with an odd one (the plausibility check, `VISIBLE_AREA`); the 3 % margin against SteamVR's reprojection of a late frame at the image's edge; the scale rule's thresholds (75 % and 60 % of the refresh interval) and its back-off, chosen from the 1.0.0.8 and 1.0.0.9 tests' GPU times and tested with made-up TIMING seconds, not yet on a PC that falls behind. A change of size makes the output images anew on the render thread (up to about 50 MB each at Native), which may cost a refresh; the back-off keeps such changes rare.

## Q. Follow-ups from 1.0.0.12's first session (1.0.0.13)

The first session of 1.0.0.12 (the same game and setup, wired, reports from both PCs) confirmed its fixes: the bitrate went back to 65 Mbit/s once the GPU clock was held, about a minute in, and never stepped down for uneven arrival; the add-on warning named only the Beyond's add-ons; about 34 ms end to end. What it showed, and what 1.0.0.13 does:
- **Packets lost in clumps.** 44 frames were rebuilt from parity and 12 lost. At the loss rate the repairs imply, random losses would almost never put two in one group of ten, and the network test on the same link lost six packets within one frame, so the wired path drops runs. `FEC_VIDEO_GROUP_WIRED` (5, `host/stream_options.py`) doubles the interleaved groups for a wired client, which rebuilds a run up to a fifth of the frame for a fifth more video data. Clients take the group count from each parity piece, so 1.0.0.9 and later repair it unchanged.
- **Where packets go missing** was in neither report. `launcher/adapter_counters.py` notes each physical adapter's counters when a session starts and reports what they gained (`adapter_counters`): packets, and every drop and error counter that moved; on Linux also UDP receive errors and the stream adapter's `ethtool -S` drop counters, on Windows `GetIfEntry2` (`launcher/windows_network.py`).
- **The decoder** fell behind at 65 Mbit/s at Native, twice, and kept up at 55; the bitrate then settled between 40 and 55. The governor already steps down for it, so nothing changes.
- **A stop while the rendering PC's SteamVR started took 88 s.** ALVR's `/api/steamvr/shutdown` reaches SteamVR only through the headset device its driver creates once a client streams, so earlier it is accepted and nothing happens; the wait then ran to the end of the 90 s launch window. `HostRuntime._shutdown_runtime` counts its window from when SteamVR's server appears and runs `vrmonitor.exe vrmonitor://quit` (SteamVR's *Exit VR*) if SteamVR still runs 5 s after the request.
- **Game Mode** failed with error 496: SteamVR's server had `WAYLAND_DISPLAY=wayland-0`, a name VROSTBridge never sets, so something between `vrstartup.sh` and the server renamed it (a container is the suspect, not confirmed). `server_origin` (`launcher/client_runtime.py`, `steamvr_origin` in the report) records the server's parents, whether it has a mount namespace of its own, the container and Steam variables it was given (names only) and which socket its display name reaches. No fix without that evidence.
- **Display modes, asked for by the maintainer after the session.** The stream size could be chosen only once a session had detected the headset: `cached_headset`, saved at every detection, never reached `display_status`. `Application.known_headset()` now offers the choices from it, or on Linux from the EDID of a known headset display connected now (`connected_family()`, the reading Game Mode uses). An Index offers *Auto* and its Native (2016 × 2240, its old High) at 80, 90, 120 and 144 Hz (`launcher/headset.py` `MODES`): the chosen rate goes into `steamvr.preferredRefreshRate` with the stream-only receipt (version 4; floats compared by value) and is put back after the session, on both systems, and a rate it did not take is logged (`DISPLAY_MODE`) and shown. A Beyond offers no choice (`resolution_fixed`): its mode is switched with Bigscreen's Beyond Utility on a Windows PC, on both systems at the maintainer's request (on Linux the Beyond shows only that mode anyway, and SteamVR would report a rate the panel is not running, the RC1.2 case). Its stream follows the mode it is in: 2560 at 75 Hz, and at 90 Hz or with H.264 1920 (`beyond-90`, what its panels take at 90 Hz). A choice the headset does not offer behaves as *Auto* and stays saved for the headset it was made for; until 1.0.0.12 another headset's choice refused the Start. An Index rate is `sharp` on the wire; a host without `display-modes` gets `sharp` (2016) instead of `beyond-90`. When the graphics fall behind, an Index is offered its next lower rate and a Beyond at 2560 is pointed at its 90 Hz mode (`sharp_preset()`).
- **The menu button:** 0.8 s after the last press the host's SteamVR re-read the controllers' bindings, and 5 s later the game quit, which suggests the dashboard opened. Not confirmed, so no change.
- **The remembered GPU clock** is now in the report (`session_tuning.remembered`, `last_session.held_from_start`); 1.0.0.12's could not say whether a session held it from the start.
- The transport's own size checks (`client/transport/lib.rs`, `tests/transport_smoke.py`) know all seven stream counters (56 bytes); two were added in 1.0.0.9.
