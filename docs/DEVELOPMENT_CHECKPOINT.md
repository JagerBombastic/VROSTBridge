# VROSTBridge handoff — 2026-10-18 / 1.0.0.14

Latest code is **VROSTBridge 1.0.0.14**, the version of every package: the Windows host, the Bazzite client and the Windows client. It answers the first external testers and 1.0.0.13's first session (section R): the controllers' acceleration folded into the poses the host predicts from, the host rendering at the headset PC's recommended size, HEVC as the automatic codec, a bitrate ceiling about a third higher, a Bazzite headset PC on its network twice kept on the cable, paired headset PCs starting on any Windows network type, the sharp region predicted through the head's turn, and the host's last session kept for its report. Its native client is rebuilt; the host's driver is 1.0.0.9's (patches 0001 to 0023). 1.0.0.11, 1.0.0.12 and 1.0.0.13 are published on GitHub; 1.0.0.14 is built and tested, with its release text ready in [GITHUB_RELEASE_1.0.0.14.md](GITHUB_RELEASE_1.0.0.14.md).

This page is the developer's handoff: where things stand, how the parts fit, how to build and test, what each release since 1.0.0.11 changed in the code (sections M to R), and what comes next. Sections A to L (1.0.0 to 1.0.0.10) are in [history/DEVELOPMENT_CHECKPOINT_EARLIER.md](history/DEVELOPMENT_CHECKPOINT_EARLIER.md). ## Where things stand

On the reference setup (Bazzite in Desktop Mode as the headset PC, wired, an AMD rendering PC encoding with AMF) sessions run routinely: the picture and tracking on an Index and a Beyond 2e, eye-tracked foveation, clean game audio, packet repair, the bitrate governor and the remembered GPU clock. The 1.0.0.14 session kept the video on the cable with Wi-Fi connected, held the GPU clock from the start and cut the controllers' worst prediction miss by about 40 %. Two things have not worked on hardware: Game Mode doesn't start sessions (SteamVR's compositor can't take the headset display), and the Windows client has run only under Wine. [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md) has the area-by-area picture.

## How the parts fit

- **Rendering PC (Windows):** SteamVR with ALVR's driver at a pinned revision plus VROSTBridge's patches (`patches/`), built without FFmpeg; the host companion (`host/`, `launcher/` in its host role) pairs headset PCs, starts and stops SteamVR for each session, sets the stream through ALVR's settings interface, and keeps reports.
- **Headset PC (Bazzite or Windows):** the client companion (`launcher/`) serves the page, runs the network test, chooses the stream, balances power and Wi-Fi, and manages eye tracking. It starts the native client (`client/`), an OpenVR scene application in the local SteamVR that receives the stream through ALVR's client core (`client/transport/`, Rust), decodes it (VA-API or D3D11VA) and shows it with one Vulkan frame pass. The companion talks to the native client over its standard input (commands such as `scale N` and `quit`) and reads its `STATUS`, `TIMING` and other lines; the gaze reaches it over a Unix socket on Bazzite or loopback UDP on Windows.
- **Between the PCs:** VROSTBridge's own session protocol (`vrostbridge-session-2`) for pairing, Start and Stop, and ALVR's stream for video, audio, tracking and input. Newer clients use newer features only when the host advertises them, so either PC can lag a release behind.

## M. A lighter picture on the headset PC (1.0.0.11)

The 1.0.0.8 test streamed 2560 per eye at 75 fps: SteamVR's GPU time per frame (`gpu_ms`, `m_flTotalRenderGpuMs`) had a median of 6.84 ms with its compositor's share (`compositor_gpu_ms`) at 2.45 ms, so about 4.4 ms of each 13.3 ms frame was the client's own GPU work (the frame pass and the plane copy), with the GPU 57 % busy. In the 1.0.0.9 test at 2016 per eye the same figures were 5.3 and 2.3 ms. With eye-tracked foveation the stream at 2560 decodes about as many pixels as Standard with fixed foveation (1408 × 1408 per eye against 1408 × 1344), so the client's pass, which grows with the shown size, was the part to make lighter for smaller GPUs.

What changed:
- **The frame pass** (`client/platform/linux/fused.comp`, `client/device/conversion.hpp` `FusedFrame`, `fusedAxis`, `fusedFrameConstants`, `client/platform/linux/vulkan.cpp` `submitFused`, `openFused`): RADV's ACO statistics on null devices (`RADV_FORCE_FAMILY` phoenix, vangogh, rembrandt; `VK_KHR_pipeline_executable_properties`), per path with the region and detail forced, showed the pass VALU-bound (periphery 232 VALU and 5 image samples per pixel, centre 254 and 10, the blend band 336 and 14, on phoenix), mostly the foveation inverse's per-pixel terms (about ten divisions per axis from uniform values, which RDNA2/3 work out per lane). The terms are now precomputed per eye, axis and region in double on the processor (each edge region as `r = sqrt(max(a m + b, 0))`, texel `= c r + d`; the centre linear; mirroring, texel scale and the eye's offset folded in; an edge ratio of 1 or an empty edge region leaves only the centre), and each eye is a workgroup layer (`gl_WorkGroupID.z`), so eye-dependent values are scalar. ACO's inverse-throughput estimate fell by 34–38 % on phoenix and 36–40 % on vangogh per path (VALU 232→150, 254→198, 336→252; VGPRs 48→32). A gather-based 4×4 neighbourhood for the centre was considered and left out: it trades image samples for arithmetic in a pass already bounded by arithmetic. Every constant now comes from a uniform buffer per output image (544 bytes, std140, written while the image is free); push constants and `fused-uniform.spv` are gone.
- **Visible spans** (`client/device/visible_area.hpp`, `OpenVRDevice::visibleArea()`): `GetHiddenAreaMesh(k_eHiddenAreaMesh_Inverse)` triangles and the outline of `ComputeDistortion` along the panel's edge (64 points a side, all three colours), each turned into a row's x-extent by its edges, intersected (after `alignMeshes`: the mesh's orientation is undocumented, so it is compared with the outline on a 128-square grid and flipped vertically when that leaves at least 2 % of the outline less out, and dropped when it leaves out over 40 % either way; a mesh without an outline gets its flipped copy added, so each row spans both orientations), widened by `visibleMargin()` (3 % of the larger side, at least 8 px) across and down; a share under 0.5 for either eye is taken for a fault. The spans (packed `first | end << 16`, both eyes) are written into each output image's storage buffer when the image is made; a new image, or one the re-aim pass filled, is cleared to opaque black before the fused pass (`needsClear`). `VISIBLE_AREA {json}` per output size; `STATUS Lens area` says whether pixels are skipped (only with the fused pass) and what `alignMeshes` did; `--full-frame` (*Skip what the lenses never show* off) keeps whole rows.
- **Showing smaller** (`launcher/output_scale.py`, `Decoder::setShownScale`, `scaledEyeSize`): see the release notes for the rule. A second counts as behind only with SteamVR's GPU time known (`gpu_ms`/`refresh_hz` at least 0.75); the settling seconds after a step are not added to the down window; a step up needs the median of the last `up_wait` seconds' known shares (at least half known) at or under 0.6. A step down within 30 s of a step up pins the size; within 300 s it counts a round trip and doubles `up_wait` (60, 120, 240, at most 480 s), and three round trips pin it. The companion sends `scale N` from `check_graphics_limit` (`send_output_scale`, under `scale_lock`, which the switch's handler also takes, and only if the size still stands; one not sent is queued again) and logs `SCALE …`; the native client applies it to `target_` in the conversion worker for the next decoded frame, so each surface keeps the size it was made at, and `shownWidth()` stays the unscaled size. *Keep the frame rate when this PC falls behind* is a live option; turning it off sends `scale 100`.
- **GPU timing**: a timestamp query pool of two per output image and one of two per copy slot (16 slots, handed out per surface), both written at `BOTTOM_OF_PIPE` around the dispatch and the copy (a `TOP_OF_PIPE` begin may be written before earlier work on the queue completes), read with availability when the image or surface is next used, scaled by `timestampPeriod` and masked to `timestampValidBits`; `frame_pass_gpu_*` and `plane_copy_gpu_*` on `TIMING`, `pass_gpu_ms`, `pass_gpu_max_ms`, `steamvr_gpu_ms` and `shown_scale` in the timeline.
- **Native**: `beyond-balanced` is labelled *Native* (`launcher/headset.py`); *Auto* still starts a Beyond at Standard.
- **Checks.** `tests/fused_shader_tests.cpp` (the pass against its CPU model with the new constants, the constants against the formula in double, the std140 offsets, visible spans in the pass), `tests/visible_area_tests.cpp`, `tests/shown_size_tests.cpp`, `tests/planar_upload_tests.cpp` and `tests/test_vrostbridge_1011.py`. New: `tests/video_pass_tests.cpp` runs `VulkanVideo` itself (open, `submitFused`, the spans and clears, the re-aim pass then the fused pass on one image, a smaller output, the time stamps) against a stand-in SteamVR generated from the OpenVR headers (`tests/make_openvr_stand_in.py`, `tests/openvr_stand_in.hpp`; `friend struct VideoTestAccess` fills a planar surface on Linux, where no VA-API decoder exists), and on Windows through `convert`/`uploadPlanes` with CPU-decoded frames under Wine; it fails if the re-aim pass stops marking its image for a clear. With the Khronos validation layer and synchronisation validation (`VK_INSTANCE_LAYERS`, `VK_LAYER_ENABLES`), it and the other Vulkan tests report nothing (a test-only readback offset in `planar_upload_tests.cpp` was aligned); a missing barrier after the clear shows as `SYNC-HAZARD-WRITE-AFTER-WRITE`, so the check bites. On lavapipe the new pass ran about a fifth faster than 1.0.0.10's in alternating runs (CPU-emulated, so relative only).
- **Open risks.** The real gain on GPUs (until the reports' `frame_pass_gpu`); headset drivers without a visible-area mesh or with an odd one (the plausibility check, `VISIBLE_AREA`); the 3 % margin against SteamVR's reprojection of a late frame at the image's edge; the scale rule's thresholds (75 % and 60 % of the refresh interval) and its back-off, chosen from the 1.0.0.8 and 1.0.0.9 tests' GPU times and tested with made-up TIMING seconds, not yet on a PC that falls behind. A change of size makes the output images anew on the render thread (up to about 50 MB each at Native), which may cost a refresh; the back-off keeps such changes rare.

## P. Follow-ups from 1.0.0.11's first session (1.0.0.12)

1.0.0.11's first session streamed well (75 new frames a second once the GPU clock was held, the sharp region following the eyes for 98.5 % of frames, about 40 ms end to end), but showed three faults:
- **The bitrate stayed low** after early losses while the GPU sat at its lowest clock, because the rendering PC's brief stalls kept making troubled seconds. `BitrateGovernor.fresh_start` returns to the starting bitrate when the session tuning raises the GPU clock, and seconds of frames that never arrived (`frames_missing`) with no network loss no longer count against it.
- **The GPU clock was found late.** `SessionTuning` remembers the held clock per PC (`gpu-clock.json`) and holds it from the next session's start while the GPU's level is automatic.
- **The add-on warning** listed SteamVR's own drivers; `host/addons.py` now lists only drivers registered from outside SteamVR's folder.

Not addressed: why SteamVR's frames sometimes reach the rendering PC's capture late (the stalls). `tests/test_vrostbridge_1012.py` holds the checks.

## Q. Follow-ups from 1.0.0.12's first session (1.0.0.13)

1.0.0.12's first session confirmed its bitrate fixes and add-on warning, at about 34 ms end to end. What it showed, and what 1.0.0.13 does:
- **Packets lost in clumps** on the wired link: `FEC_VIDEO_GROUP_WIRED` (`host/stream_options.py`) sends one parity piece per five video pieces to a wired client. Clients take the group from each parity piece, so older ones repair it too.
- **Where packets go missing:** `launcher/adapter_counters.py` reports what each adapter's packet, drop and error counters gained during a session (`adapter_counters`; on Linux also UDP receive errors and the stream adapter's driver counters).
- **A stop while SteamVR starts took 88 s:** `HostRuntime._shutdown_runtime` counts from when SteamVR's server appears and asks SteamVR to exit itself if ALVR's shutdown didn't reach it.
- **Game Mode** failed with error 496 because SteamVR's server got a display name VROSTBridge never sets; `server_origin` (`steamvr_origin` in the report) records how the server was started, to find what renamed it.
- **Display modes before a session:** `Application.known_headset()` offers the choices from the last headset seen or, on Bazzite, the one plugged in. An Index offers Native at 80, 90, 120 or 144 Hz, set in SteamVR for the session and put back after; a Beyond's stream follows the mode it is in, which Bigscreen's Beyond Utility sets.
- **The remembered GPU clock** is in the report (`session_tuning`).

`tests/test_vrostbridge_1013.py` holds the checks.

## R. The first external testers and 1.0.0.13's first session (1.0.0.14)

The 1.0.0.13 session (an hour, wired, HEVC 10-bit at Native, about 31 ms through the pipeline) ran the stream choices and the wired parity (490 frames rebuilt, 35 lost); its host report was empty because the host's companion had restarted. The first external testers found the latency good and the foveation invisible, but missed notes they had swung at in a rhythm game and found fine detail softer than on a directly connected headset. Testing the first 1.0.0.14 build found two network faults too. What 1.0.0.14 does:
- **One network, two adapters (Bazzite).** With the other Wi-Fi paused, one PC lost its route to the host and every Start failed; with Wi-Fi left on, Linux answered ARP for the cable's address on the Wi-Fi card, so the video arrived over Wi-Fi and its background scan stalled the picture every few minutes. `launcher/network_settings.py` (replacing `socket_buffers.py`) finds a PC on its subnet more than once and offers *Fix this PC's network settings*: `arp_ignore` 1 and `arp_announce` 2, with the receive buffer where needed, written to `/etc/sysctl.d/70-vrostbridge-network.conf` through one `pkexec` prompt. `wifi_others.begin(wired, separated)` then leaves Wi-Fi connected for a wired stream; otherwise it pauses Wi-Fi, checks the host's session port over the stream adapter, and on failure logs the route and undoes the pause (`resume_now`). `check_video_path` logs `VIDEO_PATH` and tells the page when the video arrives on another adapter.
- **The receive buffer, judged properly.** The stream's socket gets twice `rmem_max` (8 MiB on Bazzite); the first build read `rmem_default` as the limit and offered a fix nobody needed. Only a stream that would get under 4 MiB counts.
- **Any Windows network type.** `host/control.py` `require_home_network` needs only a connected network; `pairing_network_private` keeps the Private (or domain) requirement for a new client's automatic pairing only. Both firewall scripts create their rules with `-Profile Any -RemoteAddress LocalSubnet`, and upgraded PCs update them with one prompt.
- **The hands.** The host extrapolates from velocity alone, so a swing's acceleration left the hand short or long. `client/device/acceleration.hpp` estimates each controller's acceleration from consecutive samples (smoothed and bounded) and folds it into the pose and velocity sent, so the host's own step becomes a second-order prediction with no change to the protocol or the driver. The prediction check measures the host's result against the real pose; `prediction_acceleration` turns it off for comparison.
- **The picture.** The host renders at the headset PC's recommended size, at most 1.5 × the stream (`host/profile.py` `render_width`), and the encoder scales it down; *Auto* is HEVC unless the decoder lacks it (`automatic_codec`, with VA-API's profiles read on Bazzite by `client/platform/linux/vaapi_profiles.hpp`); the ceiling is 0.30, 0.42 and 0.25 bit per pixel for HEVC, H.264 and AV1 (`stream_budget.py`).
- **The sharp region during head turns.** `client/device/gaze_prediction.hpp` turns the gaze by the head's angular velocity over the sample's age plus the host's step, bounded at 0.35 rad.
- **The host's last session.** `launcher/last_session.py` writes `host-last-session.json` every minute and at Stop; a report with no session since the companion started carries it as `host_last_session`.
- **The menu button** is confirmed: a tester quit a game from the rendering PC's SteamVR menu.

`tests/test_vrostbridge_1014.py`, `tests/acceleration_tests.cpp` and `tests/gaze_prediction_tests.cpp` hold the checks. Not addressed: a change of direction within the latency (unpredictable on either PC), the time spent waiting for the headset PC's display, and the rendering PC's stalls.
